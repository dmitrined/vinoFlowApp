## Core Guidelines (NON-NEGOTIABLE)
1. **Zero Tolerance**: КАТЕГОРИЧЕСКИЙ запрет на `any` и `as any`. Используйте строгие типы.
2. **Verification**: Перед завершением задачи ОБЯЗАТЕЛЬНО запустить `npm run typecheck && npm run lint` в терминале.
3. **Documentation**: Каждый файл должен начинаться с блока документации на **РУССКОМ** языке (НАЗНАЧЕНИЕ, ЗАВИСИМОСТИ, ОСОБЕННОСТИ).
4. **i18n**: Полный запрет на хардкод текста. Обновлять `ru.json`, `de.json` и `en.json` одновременно.
5. **Language**: Комментарии к сложной логике внутри функций — только на русском языке.
6. **Mobile First**: Дизайн сначала для iPhone SE (375px) с использованием Tailwind CSS 4.

## 🔐 4. Безопасная типизация (TypeScript)
**КАТЕГОРИЧЕСКИЙ запрет на `any` и `as any`.**
1.  Используй точные литералы (например, `as 'active' | 'finished'`) вместо `as any`. Настроенный GitHub Actions CI/CD моментально заблокирует слияние веток при наличии `any`.
2.  Используй строгие интерфейсы для всех данных.
3.  Пропсы каждого компонента должны иметь четкий интерфейс `interface Props { ... }` или тип.
4.  Математические расчеты в `Formul...` файлах должны быть строго типизированы.

## 📦 5. Работа с данными и Sync Engine (tRPC + Prisma)
**Источник истины:** Локальный Zustand-стор с синхронизацией в облако (Turso/libSQL).

1.  **tRPC v10**: Используется для всех серверных операций. Все процедуры должны быть `protectedProcedure`, если они касаются данных брожения.
2.  **Хранилище (Zustand Persistence)**:
    *   **LocalStorage**: Для легких данных (настройки, история калькуляторов).
    *   **IndexedDB (idb-keyval)**: Для тяжелых данных (брожение, графики), превышающих 5 МБ или требующих масштабируемости. См. `idb-storage.ts`.
3.  **SyncEngine (Last Write Wins)**:
    *   Синхронизация происходит автоматически. Используй поле `updatedAt` для разрешения конфликтов.
    *   **Унификация**: Используй общую утилиту `mergeEntities<T>` из `@/lib/sync/mergeUtils` для слияния локальных и серверных массивов данных.
    *   **Состояние**: Используй стор `useSyncStore` для отслеживания флага `isSyncing` и блокировки повторных запросов.
4.  **Backend**: Схема базы данных (Prisma) должна быть строго синхронизирована с типами фронтенда в слое маппинга.

## 🔐 8. Синхронизация и целостность данных (Sync Pipeline)
При добавлении любого нового поля в сущности (Бочки, Замеры, Добавки) **обязательно** пройти по всей цепочке («Chain of Responsibility»):

1.  **DB Layer**: Добавить поле в `prisma/schema.prisma`.
2.  **Sync Types**: Описать поле в `src/types/sync.ts` (интерфейсы `Sync...`).
3.  **Zod Schema**: Обновить схему валидации в `src/server/api/routers/sync.ts`.
4.  **Mapping Layer**: Добавить маппинг поля в `src/lib/sync/mapping.ts` (функции `map...ToSync`). **Критическая точка ошибок!**
5.  **Store Layer**: Обновить интерфейс в сторе и метод `hydrateFromServer` в `useFermentationStore.ts`.

### Правило "Чистых данных":
*   **Data vs UI**: В сторах и базе данных хранятся только "чистые" значения (например, `42`, а не `Бочка №42`).
*   **Labels**: Все префиксы, единицы измерения и декоративные подписи добавляются **только** в компонентах через i18n. Запрещено хардкодить префиксы в логике маппинга.

## 🚀 9. Оптимизация и масштабируемость (Performance)
Приложение должно сохранять плавность интерфейса при 200+ бочках.

1.  **Мемоизация компонентов**: Все компоненты, являющиеся элементами списков (например, `BarrelCard`), должны быть обернуты в `React.memo`. Это предотвращает лишние перерисовки при фоновой синхронизации.
2.  **Мемоизация вычислений**: Расчеты статистики, счетчики в табах и фильтрация массивов должны выполняться через `useMemo`.
3.  **Оптимизация рендеринга**: Избегай создания анонимных функций внутри пропсов (замени на `useCallback`), если это вызывает каскадные перерисовки тяжелых веток дерева.

## 🛠 План рефакторинга (Алгоритм действий)
При внесении изменений в проект:
1.  **Анализ**: Проверь соответствие текущей схемы Prisma и типов в Zustand.
2.  **Слой API**: Опиши Zod-схему в `syncRouter` перед реализацией логики.
3.  **UI/I18n**: Вынеси все тексты в `messages/` до коммита кода.
4.  **Performance Check**: Если добавляется список или расчет — проверь необходимость `memo`/`useMemo`.
5.  **Verification (Cross-Device)**: После добавления поля проверь цикл `User A -> Cloud -> User B`. Если User B не видит данные — проверь `mapping.ts`. Используй "Rescue Button" (клик по облаку) для принудительного сброса кэша.
6.  **Контроль качества (CI/CD)**: ОБЯЗАТЕЛЬНО проверь отсутствие ошибок во всём проекте.
    *   **Zero Tolerance**: Ни один коммит не должен содержать активных ошибок TS или ESLint. Все пуши в проект автоматически валидируются через **GitHub Actions**. Любая ошибка линтера или попытка использовать `any` моментально заблокирует деплой на Vercel.
    *   **Cleanup**: Перед завершением задачи удали все неиспользуемые импорты, переменные и закомментированный код.
    *   **Локальная верификация** перед коммитом: Агент обязан самостоятельно запускать `npm run typecheck && npm run lint` локально через терминал, прежде чем сообщать разработчику об успешном выполнении работы.
    *   Сборка `npm run build` является финальной ручной проверкой. Модули `lint` и `tsc` могут пропускать ошибки, которые проявляются только при SSR/предрендеринге, поэтому CI выполняет полный билд.
7.  **Финальный шаг (Коммит)**: После успешного выполнения и проверки плана, всегда завершай работу коротким текстом для коммита в формате Conventional Commits. ПРИМЕР: `feat(seo): add dynamic i18n metadata and fix chart animations`.

## 🏛 10. Архитектура Layout (Next.js 15 App Router)

> ⚠️ **КРИТИЧНО**: Несоблюдение этих правил приведёт к полному отсутствию стилей и гидратационным ошибкам.

### Структура Layout-дерева:

```
src/app/globals.css          ← CSS + Tailwind (НЕ в [locale]!)
src/app/layout.tsx           ← КОРНЕВОЙ: <html>, <body>, globals.css, шрифты
src/app/[locale]/layout.tsx  ← ЛОКАЛЬНЫЙ: только провайдеры и навигация (БЕЗ html/body)
```

### Правила:

1.  **`src/app/layout.tsx`** (корневой) — ОБЯЗАН содержать:
    *   Теги `<html lang="...">` и `<body>`.
    *   Импорт `globals.css`.
    *   Объявление Google Fonts (Geist и т.д.).
    *   **Никакой бизнес-логики и провайдеров** — только базовая HTML-структура.

2.  **`src/app/[locale]/layout.tsx`** (локальный) — НЕ ДОЛЖЕН содержать:
    *   Теги `<html>` или `<body>` — они уже определены в корне.
    *   Дублирующие импорты `globals.css` или шрифтов.

3.  **`src/app/providers.tsx`** — ОБЯЗАН содержать:
    *   `LazyMotion` из `framer-motion` как обёртку вокруг всех провайдеров.
    *   Это предотвращает runtime-краш анимационного движка в Next.js 15.

    ```tsx
    // ✅ ПРАВИЛЬНО
    import { LazyMotion, domAnimation } from "framer-motion";
    
    <LazyMotion features={domAnimation}>
        <HeroUIProvider navigate={router.push}>
            {children}
        </HeroUIProvider>
    </LazyMotion>
    ```

## 🌍 11. Правила работы с i18n JSON-файлами

> ⚠️ Синтаксическая ошибка в `messages/*.json` приводит к полному краху сборки с неочевидной трассировкой стека.

1.  **Структура JSON**: Каждый новый namespace (блок ключей) должен быть корректно вложен в корневой объект.

    ```json
    // ❌ НЕПРАВИЛЬНО — ключи оказались вне объекта
    "Fermentation": { ... },
        "syncing": "...",      // ← ОШИБКА: вне SyncEngine!
        "synced": "..."
    },
    
    // ✅ ПРАВИЛЬНО
    "Fermentation": { ... },
    "SyncEngine": {
        "syncing": "...",
        "synced": "..."
    }
    ```

2.  **Синхронизация**: При добавлении ключа — добавить его **в все три файла**: `ru.json`, `de.json`, `en.json`.

3.  **Валидация** перед коммитом: убедиться, что JSON валиден (можно через редактор или `node -e "JSON.parse(require('fs').readFileSync('./messages/ru.json', 'utf8'))"`).

4.  **Удаление ключей**: При удалении ключа — удалять из **всех трёх файлов** одновременно, иначе возникнут предупреждения `next-intl`.
5.  **Атомарные правки**: ИЗБЕГАТЬ полной перезаписи JSON-файлов при мелких правках. Используй точечную замену (`replace_file_content`), чтобы не потерять блоки `SyncEngine`, `standards` или `formula-desc` при масштабных рефакторингах.
6.  **Контроль зависимостей**: Перед удалением или обновлением блока в JSON, проверь его использование в компонентах (например, футеры формул зависят от `Calculators.standards`).

## ⚡ 12. Известные паттерны и антипаттерны

### ❌ Не делать:

| Антипаттерн | Последствие |
|---|---|
| `src/app/layout.tsx` без `<html>`/`<body>` | Стили не подключаются, гидратационный сбой |
| `framer-motion` без `LazyMotion` в провайдере | Runtime-краш `e[o] is not a function` в вебпаке |
| Добавлять ключ только в `ru.json` | Краш на немецком и английском локалях |
| Коммитить без `npm run build` | Скрытые SSR-ошибки, не видимые в `tsc` |
| Использовать `any` в маппинге данных | Несоответствие типов при синхронизации с БД |
| Хранить `useSyncEngine` в импортах без использования | Ошибка линтера, снижение производительности |

### ✅ Делать всегда:

*   После изменений в `layout.tsx` — перезапустить dev-сервер (`rm -rf .next && npm run dev`).
*   После изменений в `messages/*.json` — проверить все три локали в браузере.
*   После добавления новой зависимости — проверить её совместимость с React 19 и Next.js 15.

## 📚 13. Knowledge Hub & Technical SEO (MDX)

1.  **MDX Стандарты**: Статьи пишутся в формате `.mdx` и хранятся в `src/content/docs/[locale]/`. Используется `next-mdx-remote` для рендеринга на сервере.
2.  **Структура Frontmatter**: Каждая статья обязана иметь `title`, `excerpt`, `author`, `date`, `readTime`, `category` и массив `relatedTools`.
3.  **Безопасный рендеринг**: Запрещено использовать интерактивные клиентские компоненты внутри MDX. Все таблицы должны писаться на чистом HTML для избежания багов парсинга (обход проблем `remark-gfm`).
4.  **Связь с калькуляторами**: Поле `relatedTools` во frontmatter содержит ID калькуляторов (например, `sr-rechner`). Этот ID маппится на реальный URL через константу `TOOL_HREFS` в `page.tsx` хаба знаний.
5.  **Technical SEO**: 
    *   `src/app/sitemap.ts` автоматически генерирует `sitemap.xml`, включая все калькуляторы и читает MDX файлы.
    *   Всегда используются языковые альтернативы (`hreflang` для ru, en, de) для предотвращения склейки страниц Google-ом.
    *   `src/app/robots.ts` управляет `robots.txt`.
